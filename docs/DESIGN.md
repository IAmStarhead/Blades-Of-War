# Blades Of War — дизайн и архитектура

**Статус:** черновик для согласования с владельцем. Это план, а не отчёт о готовой игре.
**Владелец проекта:** Роберт Сабиров (геймдизайнер, тестировщик).
**Разработчик:** агент Arena.
**Дата:** 2026-11-05.
**Ветка:** `arena/7d896124-blades-of-war`.

Документ описывает, что мы строим, на чём, в каком порядке и как проверяем результат.
Всё, что не реализовано, помечено как нереализованное. Проверенные технические факты
отделены от предположений.

---

## 1. Цель и рамки

Единая текстовая симуляционная песочница: жизнь персонажей (RimWorld), свободное
выживание и строительство (Kenshi), армии и войны (Mount & Blade), династии и политика
(Crusader Kings) — **одна связанная симуляция, а не набор отдельных режимов**.

Ключевое ограничение: мир живёт без игрока. У NPC, групп, фракций и государств есть
собственные ресурсы, интересы, цели и действия.

Игрок может пройти путь от человека без имущества до правителя, но не обязан:
нищий, торговец, воин, ремесленник, раб, рабовладелец, инквизитор, изгой, наёмник,
владелец поселения — всё это допустимые роли.

## 3. Проверенные технические факты

Проверено на практике в этой сессии, а не взято из памяти.

| Что проверялось | Результат | Как проверено |
|---|---|---|
| Компиляция `.twee` → HTML | Работает | `extwee 2.3.18` (npm) + `dist/format.js` SugarCube 2.37.3 |
| Готовый HTML | Один самодостаточный файл, ≈ 610 КБ, внешних ссылок 0 | Сборка 4 пассажей + скрипт + стили |
| Кастомный интерфейс | Работает: `StoryInterface` полностью заменяет вёрстку; обязателен элемент `id="passages"` внутри | Сборка + прогон в jsdom |
| Вынос JS в отдельный файл | Работает через пассаж с меткой `[script]` (или именем `Story JavaScript`) | Отдельный файл `010-core.twee` попал в `twine-user-script` |
| Вынос CSS в отдельный файл | Работает через пассаж с меткой `[stylesheet]` (или именем `Story Stylesheet`) | Правило из файла оказалось в DOM |
| Вызов ядра между пассажами | Работает: `<<run setup.core.advance(5)>>` изменил время, интерфейс перерисовался | Прогон: день 1, 8:00 → 13:00 |
| `StoryInit` | Требует вызова `Engine.runUserInit()` перед `Engine.start()` при ручном запуске | Без него переменные пустые — важный подводный камень для тестов |
| Сохранение SugarCube | `SugarCube.Save.serialize()` возвращает строку (≈ 228 байт на мини-сцене); `State.marshalForSave()` доступен | Прогон в jsdom |
| Реальный браузер в песочнице | **Недоступен**: Chromium скачать не удалось | `playwright install chromium` → ошибка загрузки |
| Headless-проверка логики | Доступна через `jsdom` | Прогоны выше |
| Слияние нескольких `.twee` | Сборка из каталога не поддерживается — файлы конкатенируются скриптом сборки | `extwee -i src` → «Input file 'src' does not exist» |

**Ограничение честности:** визуальную проверку (как выглядят панели, как ведёт себя
мобильная вёрстка) я в песочнице выполнить не могу. Логику, разметку и ошибки JS —
могу. Финальную визуальную приёмку делаете Вы в браузере.

## 4. Аудит существующего прототипа v0.0.1

Подробности — в `docs/PROTOTYPE_AUDIT_v0.0.1.md`. Кратко: это каркас интерфейса
с частично живой логикой. Работают: перемещение, ход времени, потребности, торговля
в движке, сохранение в JSON-строку, адаптивная вёрстка. Не работают или врут:
кнопка «Отдохнуть», стартовые события, скорость времени (×2), границы потребностей,
род NPC, валидация сохранений, двойной учёт денег.

Прототип **не является** историей Twine/SugarCube и не может быть импортирован в Twine
как есть. Это исходный материал для переписывания, а не фундамент.

## 5. Архитектура

### 5.1. Слои

```
┌──────────────────────────────────────────────┐
│  UI (пассажи SugarCube + widgets + CSS)      │  знает про SugarCube и DOM
├──────────────────────────────────────────────┤
│  Adapter (sugarcube-adapter.js)              │  единственное место стыковки
├──────────────────────────────────────────────┤
│  Systems (время, потребности, торговля, ...) │  чистая логика, без DOM
├──────────────────────────────────────────────┤
│  Core (state, события, RNG, валидация)       │  не знает про SugarCube
├──────────────────────────────────────────────┤
│  Data (JSON: товары, локации, шаблоны NPC)   │  только данные
└──────────────────────────────────────────────┘
```

Правило: **`core/` и `systems/` не обращаются к `State.variables`, `setup`, `$` и DOM.**
Они получают на вход объект состояния и возвращают результат. Это даёт возможность
позже подключить другой интерфейс (или другой движок) без переписывания логики.

### 5.2. Центральное состояние

Одно дерево состояния, живущее в `State.variables.game` (одна точка сериализации).
Черновая схема:

```js
{
  version: "0.0.2",          // версия формата сохранения
  seed: 123456,              // зерно ГПСЧ, чтобы мир воспроизводился
  time: { year, month, day, hour, minute, scale },  // scale: paused|1x|2x|8x
  player: { id, name, age, ... },
  entities: {                // все персонажи в одном словаре
    "person:1024": { id, name, age, sex, status, skills, needs, traits,
                     memory: [], relationships: {}, inventory: [],
                     health: { conditions: [] }, orgId, homeId }
  },
  orgs: {                    // фракции, ордена, банды, культы, гильдии
    "org:ice": { id, name, type, leaderId, members, goals, relations,
                 resources, laws, territory }
  },
  settlements: { "settle:1": { id, name, population, stock, buildings, market } },
  regions: { "region:north": { id, name, settlements, laws, roads } },
  items: { "item:bread": { id, name, weight, value, tags } },
  events: [],                // объективные факты (что произошло)
  knowledge: {},             // кто что знает (см. 5.5)
  journal: [],               // то, что видит игрок
  clock: { lastTick, scheduled: [] },
  flags: {}
}
```

Идентификаторы — строки с префиксом типа (`person:`, `org:`, `item:`), чтобы не путать
сущности и упрощать отладку.

### 5.3. Время и тики

- Единый календарь: час → день → месяц (30 дней) → год. Сезоны вычисляются из месяца.
- Игровое время двигается **только** через `TimeSystem.advance(hours)`.
- Все системы подписываются на тики (`onHour`, `onDay`, `onMonth`, `onYear`) и не
  двигают время сами. Это устраняет ошибку прототипа «+1 час превращается в +2».
- Пауза и ускорение меняют только `scale`; расчёт остаётся целочисленным, без «плавающих» часов.
- Долгие действия описываются как «задача с длительностью», а не как мгновенный переход.

### 5.4. События

Двухчастная модель:

1. **Факт** (objective): что случилось, где, когда, кто участники, причина (`causeId`).
2. **Знание** (knowledge): какая сущность об этом узнала, от кого, с какой версией правды.

Случайных событий «из воздуха» быть не должно: у каждого значимого события есть причина
(голод, долг, вражда, приказ, слух). Чисто случайность допускается только для погоды и
мелких происшествий.

### 5.5. Память, знания и слухи

- `memory` персонажа хранит значимые записи: кто спас, кто ударил, кто освободил,
  кто продал, кто убил родственника.
- Мелочи не хранятся поштучно — они сводятся в агрегаты (счётчики, общее впечатление).
- `knowledge` — отдельная структура: субъект → событие → источник → достоверность.
- Слух может искажаться: неверный участник, преувеличение, ложь, «испорченный телефон».
- Репутация считается **по группам**, а не одной шкалой: `reputation[orgId] = число`
  плюс отдельно «личное отношение» конкретных персонажей.

### 5.6. Статусы и право

Статус персонажа — перечисление с проверяемыми переходами:

```
free → suspect → wanted → prisoner → slave → escaped → freed / exile / deserter ...
```

Захват в плен и обращение в рабство — **разные действия** с разными последствиями.
Каждое преступление — запись с местом, свидетелями, доказательствами и законом региона.
Один и тот же поступок в разных регионах может быть преступлением, допустимой защитой
или нормой.

### 5.7. Сохранения

- Формат: `{ app: "bow", version, savedAt, checksum, game: {...} }`.
- Хранение: браузерное (штатное SugarCube) + экспорт/импорт файла `.json`.
- **Миграции:** `migrations = { "0.0.2→0.0.3": fn, ... }`; при загрузке старой версии
  применяются последовательно, а не «попытаемся как-нибудь».
- **Валидация:** проверка обязательных полей и типов до применения. Битое сохранение
  отклоняется с понятным сообщением, состояние не портится.
- Перед применением загруженных данных — снимок текущего состояния для откатов.
- Резервный слот: автосохранение перед каждым крупным обновлением.
- Честная оговорка: абсолютную совместимость всех будущих версий не обещаю.

### 5.8. Проверка данных

- Отдельный модуль `validate.js`: схемы обязательных полей, допустимые диапазоны
  (потребности 0..100, деньги ≥ 0 там, где это правило мира), ссылочная целостность
  (`leaderId` существует, `homeId` существует).
- Режим разработки: ошибки данных выводятся громко; в релизе — мягко, с записью в журнал.

  а не один сплошной файл.

## 7. Сборка и проверка

**Сборка:**

```bash
cat src/js/*.twee src/ui/*.twee src/passages/*.twee src/story.twee > build.twee
extwee -c -i build.twee -o dist/BladesOfWar.html -s vendor/format.js
```

**Почему так:** `extwee` не умеет собирать каталог, поэтому склейка — часть скрипта.
Проверено, что пассажи с метками `[script]` и `[stylesheet]` корректно попадают
в итоговый HTML.

**Проверка (то, что я могу делать сам):**
1. `node --check` по извлечённым скриптам — синтаксис.
2. Сборка HTML + проверка, что внешних ссылок `http(s)://` нет.
3. Прогон в `jsdom`: `runUserInit()` → `start()` → переходы → действия → сохранение/загрузка.
4. Проверка миграций: загрузка сохранения предыдущей версии на новом коде.
5. Проверка валидации: битый JSON, чужой файл, отсутствующие поля.

**Чего я не могу:** увидеть игру глазами и потрогать мобильную вёрстку. Это делаете Вы.
Я могу проверить наличие медиазапросов, отсутствие горизонтальной прокрутки по разметке,
размеры тач-целей в CSS — но не фактическое отображение.

## 8. Этапы

- Организации: орден-инквизиция, изгои, культы, работорговцы.
- Статусы и право: плен, рабство, побег, суд.

### Позже
Армии и осады, династии и наследование, строительство, сезоны, болезни и травмы,

## 9. Принципы «честности»

1. Кнопка без логики не попадает в сборку. Неготовое — либо скрыто, либо подписано
   «не реализовано».
2. В README и документации — только то, что проверено запуском.
3. README прототипа не переписываю молча: его утверждения противоречат коду, но это
   чужой текст, менять буду с Вашего согласия.
4. Авторский текст мира (`short story description rus.txt`) не редактирую.
5. Перед крупными изменениями — резервная копия и запись в `docs/CHANGELOG.md`.
6. Работающие механики не удаляю ради новых.

## 10. Открытые вопросы к Владельцу

1. **Нейтральный тестовый мир или сразу Эдем?** В ТЗ сказано «не придумывай сеттинг,
   используй нейтральный мир». Но у Вас уже есть авторское описание Эдема. Предлагаю:
   данные (локации, фракции, имена) держать в JSON как *тестовые*, с явной пометкой,
   а Ваш канон вписать позже одной заменой данных, не трогая код.
2. **Название поселения и фракции в 0.0.2.** «Новиград» Вы отвергли. Нужны рабочие
   варианты от Вас — или временные нейтральные («Поселение», «Отряд») до Вашего решения.
3. **`dist/*.html` в репозитории?** Плюс: можно открыть и поиграть без сборки. Минус:
   бинарно-крупный файл ≈ 600+ КБ на каждую версию. Моё предложение: хранить только
   последнюю сборку, перезаписывая её.
4. **`vendor/format.js` (612 КБ) в репозитории?** Без него сборка требует скачивания
   формата. Предлагаю хранить — тогда сборка воспроизводима офлайн.
5. **Первый играбельный фрагмент:** трактир (разговор, еда, отдых) или рынок (торговля,
   цены, NPC)? Что Вам интереснее проверить первым?
